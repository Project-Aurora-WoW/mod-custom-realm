## Часть 1. Титул «Хранитель Эха» (CharTitles.dbc)

1. Извлечь `DBFilesClient\CharTitles.dbc` из `Patch-3.mpq` (MPQ Editor).
2. Открыть в WDBX Editor. Строка 3.3.5a:
   `ID, Name_lang, NameFemale_lang, TitleMask_int1, TitleMask_int2, ...`
3. Добавить строку:
   - **ID**: `48` (следующий свободный за встроенными 1–47)
   - **Name_lang**: `Хранитель Эха` (колонка ruRU; enUS продублировать)
   - **NameFemale_lang**: `Хранительница Эха`
   - **TitleMask**: для ID 48 маска выходит за 64 бита штатной пары int —
     фактически титулы с ID > ~46 требуют проверки на тестовом клиенте
     (см. примечание ниже)
4. Сохранить `CharTitles.dbc`.

> ⚠️ **TitleMask — самая хрупкая часть.** Правило 3.3.5a: титул `ID = N`
> активируется битом `2^(N+17)` в 64-битной маске (пара int1/int2).
> Для N=47 → бит 64 → int2 = 0x00000001. Для N=48 → бит 65 → int2 = 0x00000002.
> Итоговое значение маски для SQL: `char_title_mask = int2 << 32 | int1`.
> **Обязательно перепроверить на тестовом клиенте** — поведение кастомных
> ID за пределами штатных эмпирическое.

## Часть 2. Маунт «Бездна-Пегас» (Spell.dbc + привязка к item)

### 2.1. Копия штатного спелла маунта

1. Из `DBFilesClient\Spell.dbc` взять строку штатного маунта как шаблон,
   например **spell 45991** (flying mount 310%) или **spell 40192** (ground mount).
2. Создать **новый ID** `70010` (не пересекается с серверными entry),
   скопировать строку шаблона.
3. В копии изменить:
   - **SpellName**: `Призыв: Бездна-Пегас`
   - **SpellVisualID**: при желании теневой визуал (подбор эмпирический,
     см. `SpellVisual.dbc`)
   - Остальные поля (Attributes с флагом маунта, Aura) — как в шаблоне
4. Сохранить `Spell.dbc`.

### 2.2. Модель маунта

Кастомная модель требует .m2/.skin файлов + записи в
`CreatureDisplayInfo.dbc`. Без этого используем штатный displayid,
привязанный серверно. Рекомендуемый теневой конь: displayid **24559**
или крылатый **25279** (проверить в `CreatureDisplayInfo.dbc` клиента).

> Уникальная модель — отдельная контент-задача; связка спелл↔маунт
> работает и со штатной моделью.

### 2.3. Привязка спелла к item 70003 (сервер, SQL)

После проверки спелла в клиенте создать миграцию
`sql/world/0009_mount_spell_binding.sql`:

```sql
UPDATE `item_template`
SET `spellid_1` = 70010, `spelltrigger_1` = 0, `spellcategory_1` = 76, `spellcategorycooldown_1` = -1
WHERE `entry` = 70003;
```

(`spellcategory 76` = категория маунтов, общий КД.)

## Часть 4. Упаковка MPQ

1. Собрать структуру в папке-источнике:
   ```
   DBFilesClient\CharTitles.dbc
   DBFilesClient\Spell.dbc
   ```

## Часть 4a. Дистрибуция патча (подход Waloria)

> Референс: [waloria](https://sourcecraft.dev/m-orlovrus59/waloria) (внутренний
> репозиторий с методологией модификаций 3.3.5a: лаунчер + MPQ-дистрибуция
> + AIO-аддоны). Assets репозитория — скриншоты/видео, сами DBC/MPQ
> создаются по инструкциям этой страницы.

Патч `patch-x.mpq` — файл, который нужно доставить каждому игроку.
Ручная раздача не масштабируется; у Waloria это решено **лаунчером +
веб-дистрибуцией**:

1. **Веб-каталог патчей** на сервере (любой статический хостинг):
   ```
   /patches/
   ├── manifest.json          # список патчей + версии + контрольные суммы
   ├── patch-x.mpq
   └── addons/AzerothEcho.zip # аддон тем же механизмом
   ```
2. **manifest.json** — версия, размер, sha256 каждого файла:
   ```json
   {
     "version": 2,
     "files": [
       { "path": "patch-x.mpq", "sha256": "...", "size": 1048576, "required": true },
       { "path": "addons/AzerothEcho.zip", "sha256": "...", "size": 15360, "required": true }
     ]
   }
   ```
3. **Клиентский лаунчер** (референс-реализация Waloria: Electron/Angular):
   при запуске сверяет локальные файлы с manifest.json → докачивает
   отличающиеся → чистит `Cache/` → прописывает realmlist → запуск игры.
   Минималистичный вариант — PowerShell/bat-скрипт той же логики.
4. **Обновление патча**: заменить файл в веб-каталоге + поднять `version`
   и sha256 в manifest.json — игроки получат обновление при следующем
   запуске («push change = перемещение файла по FTP»).

> ✅ **Инструментарий готов**: каталог [`../client/`](../client/) —
> шаблон `manifest.json` (заглушки SHA256 заменить после сборки) и
> PowerShell-лаунчер `update-client.ps1` (сверка manifest → докачка →
> очистка Cache → realmlist → запуск клиента). Процедура публикации
> обновлений — в [`../client/README.md`](../client/README.md).
> Остаётся: собрать `patch-x.mpq` (части 1–4) и выложить файлы на хостинг.

## Часть 4c. Конвейер DBC-кандидатов (подход wow-mod-delves)

> Референс: [wow-mod-delves](https://sourcecraft.dev/m-orlovrus59/wow-mod-delves)
> (внутренний; retail-style delves для AzerothCore). Его
> `tools/build_pilot_client.py` — профессиональный конвейер сборки
> клиентских DBC. Уровень выше ручного WDBX-редактирования; берем
> принципы, сами тулзы — при запуске деливс-пилота.

Принципы конвейера (для будущих клиентских патчей реалма):

1. **Hash-пиннинг входов**: baseline JSON связывает каждый входной DBC
   (`Map.dbc`, `AreaTable.dbc`, ...) с ожидаемым SHA-256. Сборка
   отказывается работать с непроверенным файлом.
2. **Сохранение старых строк байт-в-байт**: добавляются только новые
   записи; существующие строки и string-block не двигаются. Это
   исключает поломку ранее выданных патчей у игроков.
3. **Манифест сборки**: каждый исходник (hash), добавленные строки,
   маппинг ID, SHA-256 результата. Манифест — часть артефакта.
4. **Резервирование ID против актуальных данных**: новые ID (карт,
   областей, спеллов) проверяются на занятость по **полной цепочке
   предыдущих патчей**, а не только по одному файлу. «Локальное
   отсутствие записи — не резервация».
5. **Согласованность клиент/сервер**: строки DBC патча должны быть
   продублированы в серверных `*_dbc`-таблицах мира (либо полными
   файлами DBC на сервере) — и совпадать с клиентом.
6. **Оффлайн-проверки ≠ игровой тест**: hash-проверки и ссылки на
   файлы автоматизируются; рендер, коллизии и навигация проверяются
   только в контролируемом игровом тесте.

Связка с нашим процессом:
- текущий ручной путь (Части 1–2, WDBX) — для единичных правок;
- конвейер — когда патчей станет много (ауры Пустоты, спеллы кампаний);
- дистрибуция результата — Часть 4a (веб-каталог + manifest.json);
- готовая база MPQ — Часть 4b (`Patch-T.MPQ.rar`).

### 6.2. Порядок загрузки MPQ и правило мерджа DBC

Клиент 3.3.5a грузит `patch-*.mpq` **по алфавиту имени**, более поздний
полностью перекрывает более ранний по совпадающим файлам:

```
patch-3.mpq → ... → patch-x.mpq → patch-Z.mpq
```

**Критическое следствие:** `Map.dbc` из `patch-Z` перекрывает целиком
любой `Map.dbc` из более ранних патчей. Поэтому:

- ⛔ **В наш `patch-x.mpq` НЕ включать `Map.dbc`** — иначе при добавлении
  в него кастомных карт возникнет конфликт, и выживет только версия из
  последнего по алфавиту патча (сейчас — Z).
- Если в будущем понадобится добавить в `Map.dbc` ещё записи (свои карты),
  **мерджить DBC** на базе файла из `patch-Z` (добавлять строки, не трогая
  существующие — принцип конвейера ч. 4c, п. 2) и выкладывать в патч с
  именем **после** `patch-Z` по алфавиту (например, `patch-y.mpq` не
  подойдёт — `y` < `z`; использовать `patch-Z2.mpq` / `patch-0.mpq` и т.п.).
- Аналогичное правило для любого DBC, появляющегося в нескольких патчах:
  одна копия, самый поздний патч владеет файлом.

### 6.3. Дистрибуция

- `patch-Z.mpq` добавить в веб-каталог патчей `../client/` рядом с
  `manifest.json` (запись уже добавлена в манифест; SHA256/size заполнить
  по процедуре в `../client/README.md`).
- Лаунчер доставит файл в `WoW\Data\patch-Z.mpq` как обычный патч.

### 6.4. Серверная часть

Клиентский патч видит карту 5000, но **серверу** нужны извлечённые из
клиента **с установленным patch-Z** файлы карт (maps/vmaps/mmaps/dbc) —
см. шаг 4 гайда [`deployment.md`](deployment.md). Иначе: телепорты
Стража на карту 5000 роняют персонажа в бездну, мобы проваливаются
под текстуры, навмэши не строятся.

## Часть 8. Клиентский аддон AIO_Client

> Серверная часть AIO (v1.74, Rochet2 — референс dwrath-eluna-3-3-5a)
> уже в `lua_scripts/`. Клиентский аддон **в референсе отсутствует** —
> берём из оригинального репозитория [Rochet2/AIO](https://github.com/Rochet2/AIO)
> (каталог `AIO_Client` в корне репозитория).

### 8.1. Что такое AIO_Client

AIO — подход «всё-в-одном»: весь клиентский код (UI магазина и других
AIO-систем) живёт **на сервере** и рассылается клиенту при логине
через аддон-сообщения с LZW-сжатием. Аддон `AIO_Client` — тонкий
**контейнер/загрузчик**:

- принимает код от сервера (и проверяет кэш по CRC);
- исполняет его в клиенте (`RunScript`-механика 3.3.5a);
- отвечает на version-check сервера;
- предоставляет команды `/aio reload`, `/aio delcache`, `/aio clist`
  (управление кэшем полученного кода).

Поэтому аддон один на все AIO-системы — магазин, будущий SpellAIO и т.д.

### 8.2. Установка в патч

| Шаг | Действие |
|-----|----------|
| 1 | Скачать `AIO_Client` из репозитория Rochet2/AIO (ветка `master`) |
| 2 | Положить в структуру патча как `Interface/AddOns/AIO/` (см. ч. 7.2) — имя каталога должно совпадать с ожидаемым AIO (`AIO`) |
| 3 | Убедиться, что `.toc` указывает версию `## Interface: 30300` (3.3.5a) |
| 4 | Включить в `patch-x.mpq` при сборке (ч. 4) и дистрибутировать через лаунчер (ч. 4a) |

> Альтернатива для dev: положить `AIO_Client` в `Interface/AddOns/`
> клиента вручную — без MPQ; для прод-игроков патч обязателен.

### 8.3. Кэш аддонов

Первый логин: сервер шлёт весь код, клиент кэширует его в
`WTF\Account\<аккаунт>\SavedVariables\AIO\` (по CRC-сумме). Последующие
логины — только проверка версии. При правках `Store_Client.lua` на
сервере клиентам нужно обновление кэша: `/aio delcache` (или сброс
версии — AIO делает это автоматически при изменении CRC кода).

### 8.4. Проверка

- [ ] Аддон загружен: в списке аддонов на экране выбора персонажа есть «AIO»
- [ ] `/aio help` в чате — ответ AIO
- [ ] Логин: в чате нет ошибок AIO (ошибки приходят с traceback — StackTracePlus на сервере)
- [ ] Escape-меню → кнопка «Магазин» → UI открывается (магазин = первая AIO-система)

## Откат

Удалить `patch-x.mpq` из `WoW\Data\` — клиент вернётся к стоку
(`patch-Z.mpq` сам по себе сток не ломает — только добавляет карту 5000;
без серверных данных на неё нельзя попасть).
Серверные изменения откатываются обратной миграцией (`spellid_1 = 0`,
drop `realm_store_*`).
